# CTF Agent MVP

Работающий последовательный Python-прототип для разрешённых CTF: **задача → материалы → гипотеза → Docker-эксперимент → наблюдения → приоритеты → следующая гипотеза**. Стандартная библиотека Python, без агентных фреймворков и платного DeepSeek API.

Демонстрация использует поддельные модели, но **настоящие контейнеры и настоящий вычисляемый результат**. Заглушки моделей сами не декодируют шифротекст. Они создают карточки и скрипты, которые исполняет Runner.

## Быстрый запуск

Нужны Python 3.11+ и работающий Docker Engine / Docker Desktop. Основной CLI рассчитан на Linux/macOS (`flock`, POSIX signals). Windows — через Linux/WSL2; нативный Windows не проверялся.

Из корня проекта:

```bash
docker build -t ctf-agent-runner:local docker
python3 -m ctf_agent demo --run-dir runs/demo
python3 -m ctf_agent status runs/demo
python3 -m ctf_agent journal runs/demo
```

Ожидается `status: verified`, два эксперимента и флаг `flag{separate_roles_real_experiments}`. Первый проверяет XOR-ключ 0 и получает `NO_CANDIDATE`; второй перебирает 1..255. Проверка использует SHA-256 известного синтетического ответа, заданный генератором демонстрации как явный критерий. Сам критерий не передаётся моделям.

Без критерия результат остаётся кандидатом:

```bash
python3 -m ctf_agent demo --run-dir runs/candidate --unverified
```

Остановка после первого эксперимента и продолжение:

```bash
python3 -m ctf_agent demo --run-dir runs/resumable --stop-after 1
python3 -m ctf_agent resume runs/resumable
```

Каждый новый запуск требует нового каталога. `resume` завершённого запуска ничего не исполняет повторно. Альтернативная установка CLI: `python3 -m pip install -e .`, после чего доступна команда `ctf-agent`.

## Собственная задача

Текст — UTF-8 файл, материалы — отдельный каталог. `originals/` получает неизменную копию с SHA-256-манифестом; файлы пользователя не изменяются. Ссылки, устройства и FIFO на входе запрещены.

```bash
python3 -m ctf_agent run \
  --task-file /absolute/path/task.txt \
  --materials /absolute/path/materials \
  --category crypto \
  --config examples/config.toml \
  --run-dir runs/my-ctf \
  --max-experiments 8 --max-model-calls 60 --max-seconds 600
```

`examples/config.toml` включает живые модели. `--mode fake` подходит только для прилагаемой XOR-демонстрации с `cipher.hex`; это не универсальный решатель произвольных задач.

Для сетевой CTF каждый разрешённый endpoint задаётся явно: `--target 192.0.2.10:8080` (пример адреса, замените на адрес своей CTF), IPv6: `--target '[2001:db8::10]:8080'`. Разрешаются точные числовые IP и порты, без DNS, диапазонов и подразумеваемых портов. При отсутствии targets HTTP-инструмент запрещён. Сеть для произвольных скриптов всегда выключена.

Опциональная проверка ответа: `--expected-flag-sha256 HEX_DIGEST`. SHA-256 считается от точной UTF-8 строки флага без перевода строки. Без критерия совпадение с `flag{...}` сохраняется как `candidate_unverified`. При неверном хеше кандидат также не становится успехом. Другие форматы флагов и проверка через scoreboard пока не реализованы.

Время ограничено абсолютным deadline от создания запуска и **включает простой**. При необходимости пользователь явно продлевает время:

```bash
python3 -m ctf_agent resume runs/my-ctf --extend-seconds 300
```

Это не увеличивает лимиты модельных вызовов или экспериментов. Модель не имеет такого действия. Для исчерпанного числа вызовов/экспериментов нужен новый запуск с явно выбранными лимитами.

Новые данные можно добавить без изменения исходных файлов:

```bash
python3 -m ctf_agent add-material runs/my-ctf /absolute/path/new-clue.txt \
  --related-to originals/cipher.hex
python3 -m ctf_agent resume runs/my-ctf --extend-seconds 300
```

Данные с новым хешем увеличивают версию исследовательского состояния. Связанные приостановленные гипотезы возвращаются в очередь. `resume_when` сохраняется как текст; автоматическое возобновление использует прозрачное правило «новое содержимое, явно связанное пользователем с объектом гипотезы», а не интерпретатор произвольных логических условий.

## Архитектура и протокол

- `ctf_agent/engine.py`: цикл, очередь, бюджеты, ссылки на факты, переходы состояний, проверка кандидатов.
- `ctf_agent/adapters.py`: официальный Gemini REST, сменный локальный DeepSeek-адаптер и детерминированная демонстрационная пара.
- `ctf_agent/protocol.py`: строгие JSON-схемы и валидатор используемого подмножества. Неизвестные поля, дубли ключей, `NaN`, неверные типы и неизвестные действия отклоняются. Fenced JSON не «исправляется» автоматически.
- `ctf_agent/runner.py`: один синхронный контейнерный процесс за раз, ограничение вывода и сохранение файлов.
- `ctf_agent/storage.py`: SQLite, файловое хранилище и блокировка запуска.

Gemini получает задачу, перечень объектов, компактные последние наблюдения/отчёты, очередь, приоритеты, оставшиеся лимиты. Решения: `inspect`, `gather_info`, `interpret`, `experiment`, `reprioritize`, `suspend`, `finish`, `blocked`, `partial`. Каждое решение содержит `evidence`, `explanation`, типизированный `payload`. Все имена/формы доступны модели в схеме. Запрос внутренней цепочки рассуждений отсутствует.

Первоначальное направление задаётся категорией пользователя. При неизвестной категории Gemini указывает её в первом поручении `interpret`; до него вектор равномерный. Это эвристика. Для явно указанной `crypto` гипотеза `web` допускается только со ссылкой на зарегистрированное конкретное веб-наблюдение: HTML-компонент в материале или ответ ограниченного HTTP-инструмента.

Интерпретатор возвращает объект, конкретное утверждение, категорию, факты, альтернативы, процедуру, входы, ожидаемые положительный/отрицательный сигналы, неинформативные условия и ограничения. Он не имеет доступа к Runner. После исполнения та же роль формирует итог пары (`reporter` — фаза интерпретатора, не третий DeepSeek-агент).

Исполнитель получает утверждённую карточку. Допустимые действия: `read`, `write`, `run`, `http`, `status`, `finish`. `status` возвращает сохранённый результат процесса; отдельные фоновые процессы в этом MVP не предоставляются. Структурированный текст проверяется программой; native tool calling не предполагается. Контекст исполнителя и `conversation_id` отделены от интерпретатора. Коллизия двух сеансов блокирует запуск.

Итог пары содержит IDs, статус, наблюдения и источники, артефакты, сигнал, изменения приоритетов с основаниями и следующий шаг. Изменения передаются списком `{category, delta, reason, evidence}`; отсутствующая категория означает нулевую компоненту. Все ссылки проверяются. Ошибки, таймауты и ненулевой exit code принудительно дают `inconclusive` и нулевой вектор независимо от мнения модели. Успешный exit code сам по себе не подтверждает гипотезу: это отдельная оценка интерпретатора, сохраняемая как таковая.

## Очередь и приоритеты

Фиксированные направления: `crypto, web, reverse, pwn, forensics, misc`. SQLi/SSTI могут упоминаться в гипотезе внутри `web`, но не добавляются в вектор.

Оценка очереди: `p[category] * local_priority / (1 + attempts)`, по убыванию; при равенстве — ID. Gemini выбирает голову очереди либо предварительно меняет приоритеты/приостанавливает ветку. Это обычная очередь с детерминированной сортировкой, без MCTS.

```text
bounded_delta = clip(delta, -delta_bound, delta_bound)
u_next = clip(u + eta * bounded_delta, 0, 1)
p_next = u_next / sum(u_next)
```

Если сумма нулевая, восстанавливаются начальные оценки и выполняется нормализация. По умолчанию `eta=0.25`, `delta_bound=0.25`. Числа означают приоритет расходования бюджета, не доказанную вероятность. Каждый ненулевой сдвиг требует ссылки на наблюдение; ошибки инструмента не дают отрицательного сдвига. Полная история `u`, `p`, предложений и реально применённых дельт сохраняется.

Гипотезы имеют локальный приоритет, попытки, счётчик неинформативных попыток, статус, условия возобновления и ссылки на эксперименты. `max_uninformative` и `max_attempts` приостанавливают ветку. Приостановка не равна опровержению. Отпечаток эксперимента включает объект, процедуру, хеши входов и версию новых данных. Уже выполненный отпечаток не запускается снова даже после изменения приоритетов. Это не семантический дедупликатор: перефразирование процедуры моделью может создать новый отпечаток; общий бюджет всё равно действует.

## Docker Runner и сеть

Контейнер выполняется как UID/GID 10001, с read-only rootfs, `cap-drop=ALL`, `no-new-privileges`, лимитами CPU, памяти, PIDs, дескрипторов и размера отдельного файла; `/tmp` — ограниченный tmpfs. Монтируются только `originals` read-only и рабочий каталог конкретного запуска. Docker socket и домашний каталог не монтируются. Секреты моделей не передаются в контейнер.

Произвольные команды всегда имеют `--network none`. Доступ к HTTP реализован отдельным доверенным помощником `docker/http_fetch.py`, встроенным в образ. Только он запускается с Docker bridge-сетью, без рабочих mounts и без модельного кода: один GET к проверенной паре числовой IP/порт; без DNS, прокси, редиректов, загрузки модулей из ответа и последующих запросов. HTTPS проверяет сертификат; исключения для self-signed не реализованы. Параметры host/port не могут приходить из HTTP-ответа.

Это ограничение сети на уровне фиксированного брокера, **не firewall всего Docker bridge**. Не заменяйте доверенный Runner image произвольным образом. Raw TCP/UDP, интерактивные соединения, HTTP POST и произвольный curl из скриптов в MVP отсутствуют.

Runner ограничивает общее время команды, использует также контейнерный watchdog `timeout`, переживающий падение управляющего процесса, удаляет зависший контейнер и сохраняет exit code. Контекст получает только `output_bytes`; отдельный log содержит весь захваченный объединённый stdout/stderr до `log_bytes`. При достижении лимита процесс останавливается с `output_limit`: бесконечные полные журналы намеренно не поддерживаются. Артефакты копируются в отдельные снимки после команд, скрипты сохраняются отдельно при записи.

Остаточные ограничения: Docker не является абсолютной защитой от враждебного kernel exploit; нет отдельной VM или gVisor. Размер одного файла и последующего снимка ограничен, но жёсткая суммарная квота writable bind mount во время выполнения не установлена. Для недоверенных бинарников используйте отдельную CTF-машину/VM с дисковой квотой. Ghidra, отладчики, GPU и тяжёлые инструменты не поставляются.

## Состояние и восстановление

```text
runs/<name>/
  state.sqlite3          # runs, objects, relations, hypotheses, experiments,
                         # attempts, observations, vectors, model_calls,
                         # tool_calls, checks, budgets, events
  task.json
  manifest.json
  originals/             # неизменные копии материалов
  work/                  # рабочие файлы контейнеров
  scripts/               # версии записанных моделью скриптов
  logs/                  # полный захваченный вывод инструментов
  models/                # JSON-запросы и текстовые ответы; без API headers
  artifacts/<exp>/       # снимки результатов и report.json
  journal.json           # экспорт переходов/векторов/гипотез/проверок
```

SQLite использует WAL. Существенные переходы checkpoint-ятся; завершение эксперимента, наблюдения, вектор, статус гипотезы и проверки фиксируются одной транзакцией. Один процесс владеет запуском через `flock`.

Перед внешним действием сохраняется `running`, после него — результат. При падении между эффектом и его фиксацией результат неизвестен: восстановление удаляет контейнер и записывает `interrupted`, **не повторяя действие**. Это консервативная гарантия at-most-once, а не обещание exactly-once для внешней системы. Завершённое исполнение с ещё не полученным отчётом возобновляется на стадии отчёта. Полностью завершённый запуск повторно не работает.

Данные файлов и ответы цели отделены в контексте как недоверенные материалы. Prompt injection не может расширить программные пределы контейнера/сети/бюджета; семантическая правильность гипотезы при этом не гарантируется.

## Подключение Gemini и DeepSeek

См. [проверку документации и закреплённые ревизии](docs/integrations.md).

Gemini использует официальный `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, ключ — только `GEMINI_API_KEY` в окружении. По умолчанию строго `gemini-4-hydrogen`; модель конфигурируется, но никогда не заменяется автоматически. HTTP 404 сообщает `model_unavailable`; 401/403, 429 и отсутствие ответа имеют отдельные понятные статусы. Доступность модели для конкретного аккаунта требует живого теста.

Мост по умолчанию — **[Tsuev/opencode-deepseek](https://github.com/Tsuev/opencode-deepseek)**,
закреплённая ревизия `2e3c81d7ea47a5fabb5aa7fa2a4f45cf681981c9`.
В конфигурации: `bridge_provider = "tsuev"`. Его исходники и отдельное Python-окружение
находятся в игнорируемом `.services/opencode-deepseek`; Gemini-ключ туда не передаётся.
Скрипт установки запускается явно, обычный старт агента ничего не скачивает.

```bash
# Уже установлен в этой рабочей копии; для новой установки нужен Python 3.13.
scripts/setup_deepseek.sh

# Отдельное окно Chrome: пользователь входит сам. Cookies хранятся только в session/ моста.
python3 -m ctf_agent bridge login

# В отдельном терминале, после входа; остановка Ctrl+C.
python3 -m ctf_agent bridge start

# Проверка процесса без обращения к модели; healthz не подтверждает вход.
python3 -m ctf_agent bridge status
python3 -m ctf_agent live-check --provider bridge --config examples/config.toml
```

Вход использует отдельный профиль установленного Google Chrome, без установки/изменения
пользовательских плагинов opencode. Нужные проверки проходят вручную. Обёртка не печатает
даже префикс токена и отключает дополнительные browser launch args upstream. Права вновь
создаваемых файлов ограничены `umask 077`. Программа не читает пользовательский Chrome-профиль.

Управляемый запуск сервера отключает автоматический вход, фоновый refresh и неявное
сопоставление истории (`CONVERSATION_REUSE=0`). Передаются явные `conversation_id`.
Паузы, квоты и cooldown самого моста остаются с безопасными upstream-значениями.
`model_seconds=120` учитывает время ожидания в его очереди. `reporter` продолжает сеанс
интерпретатора; совпадение ID диалога с исполнителем блокируется даже при разных ID сообщений.

Gemini можно передать без записи в историю shell:

```bash
python3 -m ctf_agent live-check --provider gemini --config examples/config.toml --prompt-key
# Тот же флаг поддерживают run и resume; ключ существует только в памяти процесса.
```

Для обычного запуска по-прежнему поддержан `GEMINI_API_KEY` в окружении. Ни ключ, ни
authentication headers не записываются в конфигурацию/журналы. `gemini_output_tokens`
задаёт максимум вывода; smoke-проверка использует уровень `low` и предел 2048 токенов.

`deepseek-chat` — имя режима моста; приложение не утверждает соответствие конкретной версии официальной модели. Только текст, `stream=false`, `thinking=false`, `search=false`. `conversation_id` сохраняется отдельно для каждой роли. На 401/403/429/503 и ошибки соединения запуск становится `blocked`, состояние сохраняется; повторов автоматически нет. После ручного устранения причины можно явно вызвать `resume`. `503 login_required` распознаётся отдельно; числовой `Retry-After` сохраняется без автоматического повтора. Upstream может заворачивать различные внутренние отказы в общий HTTP 500: в этом случае сохраняется `service_error`, без угадывания причины и без вывода потенциально чувствительного тела ошибки.

## Проверки

```bash
# Без Docker и без внешних моделей:
python3 -m unittest tests.test_core -v

# С реальным Docker и установленным мостом, без внешних генераций:
CTF_TEST_DOCKER=1 CTF_TEST_TSUEV=1 python3 -m unittest discover -v

# Отдельные живые проверки, только когда настроены ключ/сессия:
python3 -m ctf_agent live-check --provider gemini --config examples/config.toml
python3 -m ctf_agent live-check --provider bridge --config examples/config.toml
```

`live-check` не выводит ключи, cookies или ID сеанса. Секреты в конфигурацию не записываются; журнал модельных запросов содержит контексты и схемы, но не HTTP authentication headers. Ответы очищаются от точных значений известных секретов окружения. Материалы CTF и обычный вывод инструментов сохраняются как данные — не помещайте в них посторонние секреты.

Обновление интеграции Tsuev и живые проверки: [docs/tsuev-validation.md](docs/tsuev-validation.md).

Результаты первоначальной проверки и ограничения живых тестов: [docs/validation.md](docs/validation.md). Пример реальной истории демонстрации: [examples/demo-journal.json](examples/demo-journal.json).
